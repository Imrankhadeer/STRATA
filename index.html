What we're building

Security that connects events, not just alerts.

A suspicious event rarely tells the whole story. The useful signal often appears across service boundaries, over time, and in context.

CAPABILITY / 01

Cross-service correlation

Bring related runtime and application events into a shared timeline to make multi-step behavior easier to investigate.

CAPABILITY / 02

Evidence-led investigation

Use AI to examine suspicious sequences, compare plausible explanations, and reference the evidence behind each finding.

CAPABILITY / 03

Validated detections

Turn useful discoveries into constrained, versioned detectors—after testing against both suspicious and benign scenarios.

Operating model

Discover once. Detect reliably.

Routine detection stays fast and deterministic. AI is reserved for investigation and discovery—not every event that enters the system.

01

Observe

Normalize telemetry from applications, services, and runtime tools into a consistent event stream.

02

Investigate

Correlate unusual behavior and use the model to evaluate hypotheses against available evidence.

03

Validate

Replay candidate detections against held-out suspicious and benign scenarios before approval.

04

Verify

Deploy approved detectors with audit history. Gate response actions and verify their actual outcome.

Architecture direction

Built to fit into the security stack.

Ternline is intended as an intelligence and orchestration layer—not a replacement for telemetry collectors, runtime sensors, network policy, or existing security controls.

The initial prototype uses simulated service telemetry. Integrations with established tools can follow once the core detection and evaluation loop is working.

A

Telemetry inputs

Application events, service activity, and compatible observability or runtime-security signals.

B

Detection core

Event normalization, baseline checks, temporal correlation, and deterministic detector execution.

C

Investigation and knowledge

Model-assisted analysis backed by evidence references, incident history, and persistent detector versions.

D

Policy and verification

Explicit authorization, auditable actions, outcome checks, and rollback paths for supported responses.

Engineering principles

Trust has to be earned by the system.

Security automation needs more than a convincing explanation. Findings must be testable, actions controlled, and outcomes observable.

↗

Evidence over assertion

Investigations should point to source events and distinguish observed facts from hypotheses.

↗

Evaluation before promotion

New detectors must pass repeatable tests, including benign lookalikes, before becoming active.

↗

Least privilege by default

Model-generated suggestions cannot directly execute arbitrary code or bypass policy controls.

↗

Measured performance

Detection quality, false positives, latency, model usage, and response outcomes should be measured—not assumed.

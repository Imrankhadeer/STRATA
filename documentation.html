Hands-On Tutorial: Zero to First Threat in 3 Minutes

Never worked with a security event engine, SOC tool, or microservice correlation system before? Ternline is designed specifically for software engineers. Follow this 5-step walkthrough to start the local engine, send a sample telemetry event, trigger a real-time brute force alert, and actively quarantine the attacker.

Ternline in 30 Seconds: The Plain-English Mental Model

Modern microservices produce thousands of distributed API logs. Ternline acts as an automated security co-pilot that watches these logs and acts instantly:

📡 1. Microservices Emit

Whenever a user logs in, queries a database, or transfers funds, your microservice sends a lightweight JSON event to Ternline at POST /v1/events.

⚡ 2. Fast Track Correlates

Ternline correlates events across multiple services by trace ID or client IP in real time. If 5 failed logins occur in 60s, it instantly creates a Security Finding with proof.

🛡️ 3. Active Defense Quarantines

You review findings in the Control Room. With 1 click (or via automated policy), Active Defense revokes compromised keys or quarantines the attacker IP at the perimeter.

1

Launch the Ternline Engine

Choose either Docker Compose (includes PostgreSQL & Redis) or direct Python execution:

docker compose up -d

Verify that the service is running and ready to accept traffic:

Open the Live Control Room

Open your browser and navigate to the SOC Console UI:

http://localhost:8000/console ↗

You are now inside the Ternline SOC Control Room. You will see real-time gauges: Ingestion Rate, Active Findings, High-Priority Incidents, and Active Defense status. It polls the engine automatically every 3 seconds.

3

Send Your First Telemetry Event

Simulate an authentication gateway service reporting a normal customer login attempt:

curl -X POST http://localhost:8000/v1/events \
  -H "Authorization: Bearer YOUR_TERNLINE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "app_id": "payments-api",
    "service_id": "api-gateway",
    "event_type": "auth.login_attempt",
    "severity": "low",
    "source_resource": "198.51.100.42",
    "target_resource": "/api/v1/login",
    "attributes": {
      "username": "alice@example.com",
      "auth_method": "password"
    }
  }'

The engine responds with HTTP 200 OK:

{
  "status": "accepted",
  "event_id": "evt_01HZX82P9J7V2R4M80KB5N29",
  "finding_id": null
}

Check your Control Room: Switch to the Event Explorer tab or watch the Ingestion Counter tick up by 1. The event was validated, correlated, and persisted to PostgreSQL in milliseconds.

4

Trigger a Live Attack Alert

Now simulate a real attacker attempting a brute-force credential spray from IP 198.51.100.42. Ternline's built-in detector.auth.brute_force triggers when 5 failed logins occur within 60 seconds from the same source IP:

Run 5 rapid failed logins (macOS / Linux / Bash):

for i in {1..5}; do
  curl -s -X POST http://localhost:8000/v1/events \
    -H "Authorization: Bearer YOUR_TERNLINE_API_KEY" \
    -H "Content-Type: application/json" \
    -d "{\"app_id\":\"payments-api\",\"service_id\":\"api-gateway\",\"event_type\":\"auth.login_failed\",\"severity\":\"medium\",\"source_resource\":\"198.51.100.42\",\"target_resource\":\"/api/v1/login\",\"attributes\":{\"attempt\":$i}}"
done

Windows PowerShell alternative:

1..5 | ForEach-Object {
  Invoke-RestMethod -Uri "http://localhost:8000/v1/events" -Method Post -Headers @{"Authorization"="Bearer YOUR_TERNLINE_API_KEY"} -ContentType "application/json" -Body '{"app_id":"payments-api","service_id":"api-gateway","event_type":"auth.login_failed","severity":"medium","source_resource":"198.51.100.42","target_resource":"/api/v1/login"}'
}

On the 5th event, the engine recognizes the sliding window threshold violation and immediately generates a Security Finding:

{
  "status": "accepted",
  "event_id": "evt_01HZX82P9J7V2R4M80KB5N35",
  "finding_id": "fnd_01HZX82PBW7E1D8M92AC1K44"
}

Instant Alert in Control Room: Switch to the Findings tab. A HIGH severity alert appears: Brute Force Credential Spray Detected. Click on it to see the full list of correlated failed login events, timestamps, and target resources attached as evidence.

5

Quarantine the Attacker with Active Defense

Contain the threat immediately so the attacker cannot continue probing your infrastructure:

Option 1: Point-and-Click in the Control Room

In the Findings tab, click the newly generated finding, then click "Propose IP Quarantine" or "Execute Containment". Active Defense immediately registers the block.

Option 2: Direct Active Defense API Call

curl -X POST http://localhost:8000/api/v1/defense/quarantine/ip \
  -H "Authorization: Bearer YOUR_TERNLINE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "ip": "198.51.100.42",
    "reason": "Exceeded failed login threshold (Brute Force)",
    "duration_seconds": 3600
  }'

Verify Containment: Try sending another event from IP 198.51.100.42 (repeat Step 3). Ternline immediately denies the request at the perimeter with HTTP 403 Forbidden:

{
  "detail": "Source IP '198.51.100.42' is actively quarantined by Active Defense until 2026-11-02T22:50:00Z"
}

The attacker is contained. Your downstream microservices were never touched, and the quarantine automatically expires in 3600 seconds or can be rolled back anytime via the Control Room.

System Architecture

Ternline structures workloads across two decoupled operating tracks to balance high-throughput telemetry ingestion with deep forensic analysis:

FAST TRACK

Deterministic Ingestion & Pattern Detection

Operates synchronously during the POST /v1/events request lifecycle in Python 3.12+ with in-memory state or Redis 7+ atomic sliding windows. Evaluates declarative rules and native baseline detectors, persists validated events to PostgreSQL, and records security findings. Never places synchronous LLM API calls on the ingestion path.

DEEP TRACK

AI Forensic Investigation & Hypothesis Synthesis

Operates strictly out-of-band. Triggered manually by operators or automatically for critical findings. Gathers distributed trace context across services via EvidenceCollector, audits generated citations against PostgreSQL database records using InvestigationQualityAuditor, and proposes candidate declarative detection rules for human review.

Connect Your Application to Ternline

Send security events from your application to Ternline in a few minutes. Ternline works with independent applications and services. You can integrate it with FastAPI, Django, Flask, Express, NestJS, Go, Java, or any system capable of sending HTTP requests.

1️⃣ Register Application

Create an application in Ternline, assign an environment (Production, Staging, Dev), and generate a cryptographically hashed API key.

2️⃣ Install & Configure SDK

Install cyber-engine-sdk or use the REST API. Set TERNLINE_ENDPOINT and TERNLINE_API_KEY environment variables.

3️⃣ Stream Telemetry & Protect

Emit security events on authentication, authorization, or sensitive operations. Fast Track evaluates events in <1ms for real-time defense.

1

Create an Application

  1. Sign in to the Ternline Control Room (or hosted deployment at https://ternline.vercel.app/console).
  2. Select your workspace using the workspace selector dropdown in the top navigation bar.
  3. Navigate to Applications & SDK (or open Platform Settings → Applications & Keys).
  4. Click Add Application (or + Register Application).
  5. Enter your application name and select its environment:
SettingExample ValueDescription
Application nameCheckout APIHuman-readable microservice or system title
EnvironmentProductionTier classification (Production, Staging, Development)
Application IDcheckout-apiUnique slug identifier bound to ingestion scope

After creating the application, open its integration settings to view and copy its provisioned API key.

Keep your API key secret: Copy it when it is displayed. Store it in an environment variable or secrets manager (AWS Secrets Manager, HashiCorp Vault, Doppler). Never commit it to GitHub or expose it in frontend JavaScript.

2

Install the SDK

For Python applications (FastAPI, Django, Flask, Celery):

pip install cyber-engine-sdk

For Node.js / TypeScript, Go, Java, or other runtimes, use the supported SDK or the standard HTTP REST API (POST /v1/events).

3

Configure Your Application

Set the following environment variables in your deployment environment or .env file:

TERNLINE_ENDPOINT=https://ternline-cyber-engine.onrender.com
TERNLINE_API_KEY=YOUR_TERNLINE_API_KEY

Use the actual API endpoint provided by your Ternline deployment (e.g. your AWS EC2 host or Render domain). Do not hardcode credentials in your source code.

Python Integration

Initialize the client once when your application starts:

import os
from cyber_engine import CyberEngine

ternline = CyberEngine(
    api_key=os.environ["TERNLINE_API_KEY"],
    app="YOUR_APPLICATION_ID",
    endpoint=os.environ["TERNLINE_ENDPOINT"],
)

The application ID must match the application associated with your API key.

4

Send Your First Security Event

Add telemetry to important parts of your application, such as authentication, authorization, sensitive data access, and administrative actions.

Example: Recording a failed login attempt:

ternline.emit(
    event_type="auth.login.failed",
    service="auth-service",
    severity="medium",
    details={
        "client_ip": "203.0.113.10",
        "reason": "invalid_password",
    },
)

This is an illustrative example. Use the SDK's actual supported method signature and event fields for your installed version. Avoid sending passwords, access tokens, session cookies, or other sensitive information.

2

Verify Your Connection

  1. Start your application.
  2. Trigger an action that emits a security event (e.g. attempt an invalid login or make an API request).
  3. Open the Ternline Control Room.
  4. Select your application from the topbar filter.
  5. Open Event Explorer in the sidebar.
  6. Confirm that the event appears with its service ID, event type, and attributes.

Verification Standard: A successful connection should be based on actual telemetry received by Ternline, not simply the existence of an API key.

If your event does not appear, check:

  • The API endpoint: Ensure TERNLINE_ENDPOINT matches your active engine host without trailing slashes.
  • The application API key: Ensure the Authorization: Bearer YOUR_TERNLINE_API_KEY header is correctly transmitted.
  • The application ID: Ensure app_id in the payload matches the application scope of the API key.
  • Network connectivity: Verify firewall, VPC egress, or proxy rules allow HTTPS requests to the Ternline backend.
  • The event payload: Ensure all required fields (app_id, service_id, event_type) are present and conform to alphanumeric patterns.
  • The ingestion response: Check the HTTP status code (HTTP 202 Accepted indicates success; HTTP 422 indicates validation failure).

5-Minute Onboarding Workflow

This workflow walks through provisioning an ingestion key, emitting telemetry, and viewing detected intelligence.

Environment Context: The examples below target a local development engine at http://localhost:8000. For production, replace the endpoint with your cloud backend URL (e.g. https://api.yourdomain.com) and use your workspace credentials.

1

Provision an Ingestion API Key

API keys are SHA-256 hashed and scoped to a specific tenant_id and app_id. Provision a key using an administrative operator token or via the Control Room:

curl -X POST http://localhost:8000/api/v1/keys \
  -H "Authorization: Bearer YOUR_OPERATOR_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "app_id": "payments-api",
    "name": "Checkout Ingest Key"
  }'

The server returns a plaintext key prefixed with ce_live_. Store this key securely; only its SHA-256 hash is retained in the database.

2

Emit Canonical Telemetry

Send a telemetry event to /v1/events using the provisioned key. The app_id in the payload must match the application scope of the API key:

curl -X POST http://localhost:8000/v1/events \
  -H "Authorization: Bearer YOUR_TERNLINE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "app_id": "payments-api",
    "service_id": "checkout-worker",
    "event_type": "auth.login_failed",
    "severity": "medium",
    "source_resource": "198.51.100.42",
    "target_resource": "/api/v1/auth/login",
    "trace_id": "trace-8f0ef82b-101",
    "attributes": {
      "user_id": "usr_9981",
      "failure_reason": "invalid_password",
      "attempt_count": 3
    }
  }'

Successful Response (HTTP 202 Accepted):

{
  "accepted": 1,
  "rejected": 0,
  "duplicates": 0,
  "event_ids": ["c1a4569e-561b-4f7d-8fb0-4573199bc489"],
  "errors": [],
  "correlation_status": "ok",
  "correlation_degraded_reason": null
}

Common Ingestion Errors:

  • HTTP 401 Unauthorized: The Bearer token is missing, invalid, or revoked.
  • HTTP 403 Forbidden: The event's app_id does not match the key's application scope, or the source IP address is quarantined by Active Defense.
  • HTTP 422 Unprocessable Entity: Missing required fields (app_id, service_id, event_type) or invalid attribute key formats.
  • HTTP 429 Too Many Requests: Tenant rate limit exceeded (default: 1,200 events/minute).
3

View Real-Time Security Intelligence

Open the Ternline Control Room. Telemetry streams into the Event Explorer, Fast Track evaluates events against declarative rules, the Incident Correlator groups multi-service activity, and Active Defense monitors containment policies.

Launch & Configure Ternline

This is the operator setup path: prepare the database and runtime configuration, start the API, verify dependencies, then connect the web console. Keep development and production credentials separate.

1. Prerequisites

  • Python 3.12+ for direct execution, or Docker Engine with the Docker Compose plugin.
  • PostgreSQL 16. Ternline uses PostgreSQL; SQLite is not supported.
  • Redis 7+ for distributed correlation and shared runtime state, especially when running multiple API workers.
  • A configured AI investigation provider and its API credential if Deep Track investigations are enabled.

Run commands from the repository root (the directory containing requirements.txt, backend/, and the Alembic configuration). Use the compose file and environment template that actually exist in your checkout; do not copy a guessed filename or repository URL from an example.

2. Start with Docker Compose

Use the repository's Compose configuration when it defines the API, PostgreSQL, and Redis services. Start the stack, then inspect logs before testing the API:

docker compose config
docker compose up -d
docker compose ps
docker compose logs -f

If your checkout uses a named Compose file, pass it explicitly with -f (for example, docker compose -f docker-compose.prod.yml up -d) and use the matching environment file documented for that deployment. Do not assume the production Compose file is suitable for local development.

3. Start directly with Python

For a local development run, first make sure PostgreSQL and Redis are running and the environment variables below point to them. Then install dependencies, apply migrations, and start the API:

python -m venv .venv
# Windows PowerShell:
.venv\Scripts\Activate.ps1
# macOS / Linux:
# source .venv/bin/activate

pip install -r requirements.txt
alembic upgrade head
uvicorn backend.main:app --host 127.0.0.1 --port 8000 --workers 1

Keep the API bound to 127.0.0.1 for local-only development. Bind to 0.0.0.0 only when the service must be reachable from another container or host and the network is appropriately restricted.

4. Configure environment variables

Set these in your shell, deployment environment, or a locally ignored .env file. Never commit secrets or paste them into frontend JavaScript.

Apply migrations before serving traffic. For a new production deployment, follow the repository's documented bootstrap procedure to create the first administrator; do not enable development key seeding.

alembic upgrade head

Check the health response and service logs for PostgreSQL and Redis status. A healthy HTTP response alone should not be interpreted as proof that every optional integration is configured.

  1. Deploy or serve the static frontend separately from the backend API.
  2. Configure the frontend's API base URL using the actual supported frontend configuration mechanism in your checkout.
  3. Add the exact frontend origin to ALLOWED_CORS_ORIGINS.
  4. Open the console, register or sign in, create a workspace/application, and generate an application-scoped ingestion key.
  5. Configure your application with TERNLINE_ENDPOINT and TERNLINE_API_KEY, send a test event, and confirm it appears in Event Explorer.

Do not expose operator JWT signing secrets, database credentials, Redis credentials, or ingestion keys in the browser bundle. The ingestion key belongs in the instrumented server-side application.

7. Before exposing a deployment publicly

  • Use HTTPS and restrict database/Redis access to the backend network.
  • Set production secrets through the hosting provider's secret manager.
  • Set exact CORS origins and review authentication, email verification, and initial-admin bootstrap.
  • Use PostgreSQL backups and test restore procedures.
  • Confirm Redis availability and worker configuration before scaling horizontally.
  • Start protection in OBSERVE mode; explicitly review policy and approval requirements before enabling enforcement.
  • Verify health, metrics, logs, and the live event stream after deployment.

Authentication & Identity Models

Ternline enforces strict multi-tenant boundary isolation across two distinct authentication models:

Identity ModelToken TypeTarget ScopeAllowed Operations
Service Ingestion Key Hashed API Key (ce_live_...) Application-scoped (app_id) Telemetry ingestion (POST /v1/events, POST /v1/events/batch) and diagnostic testing.
Operator Session Token Cryptographic JWT (HS256) Tenant-scoped Human Operator Rule authoring, dual-custody action approvals, containment execution, investigations, policy updates.

Anti-Spoofing Enforcement: Human actions such as containment approvals (/api/v1/defense/actions/{action_id}/approve) require a verified operator JWT. Ingestion API keys and service accounts are strictly rejected from approving containment actions.

Canonical Event Schema

All telemetry events must conform to the Canonical Event Schema. Fields are validated upon arrival, and payload size is bounded to 1 MB per request.

FieldTypeRequiredConstraints & Description
app_idstringYesApplication identifier. Must match the API key's application scope. Pattern: ^[a-zA-Z0-9_\-\.]+$ (1-64 chars).
service_idstringYesMicroservice or worker name (e.g. api-gateway, payment-processor). Pattern: ^[a-zA-Z0-9_\-\.]+$ (1-64 chars).
event_typestringYesDot-separated event classification (e.g. auth.login_failed, db.bulk_query). Pattern: ^[a-zA-Z0-9_\-\.]+$ (3-128 chars).
event_idstring (UUID)NoGlobally unique event identifier. Server generates a UUID v4 if omitted.
schema_versionstringNoSemantic version of event schema. Defaults to "1.0.0".
timestampstring (ISO-8601)NoUTC timestamp of event occurrence. If omitted, server assigns current UTC time. Naive timestamps are converted to UTC.
severityenumNoOne of "info", "low", "medium", "high", "critical". Defaults to "info".
source_resourcestringNoOriginating client IP, user ID, or service ARN (max 256 chars).
target_resourcestringNoTarget endpoint, table name, or RPC method (max 256 chars).
trace_idstringNoDistributed W3C / OpenTelemetry trace identifier across service hops (max 128 chars).
request_idstringNoHTTP or correlation request ID (max 128 chars).
attributesobject (JSON)NoStructured context map. Max 200 keys; keys must be alphanumeric (max 64 chars).
provenanceobject (JSON)NoSensor, host, runtime environment, or SDK version metadata.

Python SDK Guide

The native Python client (cyber_engine) provides buffered and non-buffered event dispatch with automatic secret scrubbing, payload bounding, and HTTPS verification.

Package Import: The official library is imported as from cyber_engine import CyberEngine.

from cyber_engine import CyberEngine, IngestError

# Initialize client
client = CyberEngine(
    endpoint="https://api.yourdomain.com",  # Enforces HTTPS for remote hosts
    api_key="YOUR_TERNLINE_API_KEY",
    app="payments-api",
    service="checkout-worker",
    buffered=True,                          # Non-blocking background worker thread
    buffer_size=1000,
    flush_interval_seconds=2.0,
    max_batch_size=50,
    auto_sanitize=True,                     # Automatically scrubs PII and passwords
    max_retries=3
)

# Emit telemetry event
try:
    result = client.emit(
        event_type="auth.login_failed",
        severity="medium",
        source_resource="198.51.100.42",
        target_resource="/api/v1/auth/login",
        trace_id="trace-0192a-88",
        attributes={
          "user_id": "usr_789",
          "failure_reason": "invalid_password",
          "password": "plain_secret_text"   # Auto-redacted to [REDACTED] before transmission
        }
    )
    print(f"Accepted: {result.accepted}, Event ID: {result.event_ids}")
except IngestError as e:
    print(f"Ingestion rejected: {e}")

Client-Side Sanitization Details

When auto_sanitize=True (default), the SDK scrubs sensitive keys using regex matching on:

password, passwd, pwd, secret, api_key, access_token, auth_token, authorization, bearer, jwt, private_key, credit_card, cvv, ssn.

Strings longer than 10,000 characters are safely truncated to prevent buffer overflows.

Multi-Language Ingestion Patterns

Ternline officially distributes the native Python SDK. For Go, Node.js, and Java, services integrate via standard HTTP POST calls conforming to the Canonical Event Schema.

Go Integration Pattern

package main

import (
    "bytes"
    "encoding/json"
    "net/http"
    "time"
)

type Event struct {
    AppID          string                 `json:"app_id"`
    ServiceID      string                 `json:"service_id"`
    EventType      string                 `json:"event_type"`
    Severity       string                 `json:"severity"`
    SourceResource string                 `json:"source_resource,omitempty"`
    TraceID        string                 `json:"trace_id,omitempty"`
    Attributes     map[string]interface{} `json:"attributes,omitempty"`
}

func emitTelemetry(ev Event) error {
    body, _ := json.Marshal(ev)
    req, _ := http.NewRequest("POST", "http://localhost:8000/v1/events", bytes.NewBuffer(body))
    req.Header.Set("Authorization", "Bearer YOUR_TERNLINE_API_KEY")
    req.Header.Set("Content-Type", "application/json")

    client := &http.Client{Timeout: 3 * time.Second}
    resp, err := client.Do(req)
    if err != nil {
        return err
    }
    defer resp.Body.Close()
    return nil
}

Fast Track Detection & Declarative Rules

Detection Pipeline & Performance

The Fast Track pipeline processes incoming telemetry through the following deterministic phases:

HTTP Ingest → Schema Validation → Tenant Rate Limiting → Active Defense Containment Filter → Sliding Window State → Declarative Rule Evaluation → PostgreSQL Event Storage → Security Finding Creation → Auto-Incident Correlation.

Latency Profile: Rule evaluation operates purely in-memory and via atomic Redis Lua scripts without external network calls. Total end-to-end HTTP request latency is dominated by network roundtrip and PostgreSQL persistence (typically low double-digit milliseconds depending on database latency).

Declarative Rule Structure

Rules contain zero executable expressions (Python eval, shell scripts, or raw queries are rejected at schema validation). Rules target either native detector engines or generic declarative specifications:

Example: Generic Threshold Rule Proposal

{
  "target_detector": "detector.auth.failed_threshold",
  "title": "Rapid Authentication Failure Spikes",
  "description": "Flags accounts receiving >= 5 failed logins within 60 seconds",
  "parameters": {
    "failure_threshold": 5,
    "window_seconds": 60.0
  }
}

Example: Cross-Service Exfiltration Rule

{
  "target_detector": "detector.cross_service.exfiltration",
  "title": "Sensitive Table Bulk Extraction Sequence",
  "description": "Correlates database read spikes followed by worker egress",
  "parameters": {
    "time_window_seconds": 300.0,
    "bulk_row_threshold": 1000,
    "sensitive_tables": ["users", "credit_cards", "tokens", "secrets"],
    "internal_prefixes": ["/api/v1/internal/", "/internal/", "/admin/export"]
  }
}

Supported Comparison Operators

Generic rule field conditions evaluate against an explicit operator allowlist:

equals, not_equals, in, not_in, starts_with, starts_with_any, ends_with, contains, gt, gte, lt, lte, exists, is_true, is_false.

Rule Validation, Approval & Promotion Lifecycle

Rules progress through mandatory state transitions:

  1. Proposed (status: proposed): Created via POST /api/v1/rules or synthesized by Deep Track AI.
  2. Replay Validation (POST /api/v1/rules/{id}/validate): Replays historical attack scenarios through ReplayValidationEngine. Calculates true positives, false positives, precision, recall, and F1 score. Rules failing the validation threshold cannot be approved.
  3. Approval (POST /api/v1/rules/{id}/approve): A human operator reviews validation metrics and authorizes the rule with an audit rationale.
  4. Activation (POST /api/v1/rules/{id}/activate): Instantiates the rule in runtime_rule_registry for real-time evaluation.
  5. Disable / Rollback (POST /api/v1/rules/{id}/disable, POST /api/v1/rules/{id}/rollback): Deactivates rule or reverts to previous approved version with audit recording.

Distributed State & Degradation Modes

  • Redis Available: Correlation state and sliding windows are synchronized in Redis 7+ via atomic Lua scripts. Supports horizontally scaled multi-worker deployments.
  • Redis Unavailable (Degraded Mode): When Redis is unreachable and REDIS_REQUIRED=false, the engine falls back to process-local in-memory sliding windows. Telemetry ingestion continues, returning correlation_status: "degraded". In production multi-worker clusters, REDIS_REQUIRED=true must be set to ensure cross-worker correlation.

Deep Track AI Investigation

Deep Track provides forensic root-cause analysis and hypothesis generation using configurable LLM providers (Meta Muse, OpenAI-compatible, or mock).

Triggering Investigations

  • Manual Finding Triage: POST /api/v1/investigations/{finding_id} runs investigation on an existing Fast Track finding.
  • Ad-Hoc Forensic Search: POST /api/v1/investigations/query runs an investigation prompt against stored telemetry.
  • Live Streaming: POST /api/v1/investigations/query/stream streams reasoning progress via Server-Sent Events (SSE).

Evidence Collection & Citation Auditing

To eliminate hallucinated evidence, Deep Track enforces two architectural controls:

  1. Database Grounding: The EvidenceCollector queries PostgreSQL for events matching the trace ID, actor, and affected microservices within the incident time window.
  2. Mathematical Citation Auditing: The InvestigationQualityAuditor parses every event ID cited in the model's reasoning and verifies its existence in the database. Any citation referencing a non-existent or fabricated event ID is rejected.

AI Scope & Trust Boundaries

Strict Advisory Boundary: Deep Track AI is strictly an advisory engine. It has read-only access to telemetry records. It cannot execute containment actions, modify database records, or activate detection rules. All candidate rules generated by AI require human operator review, replay testing, and explicit approval.

Queries submitted to /api/v1/investigations/query pass through an automated scope gatekeeper (backend/investigation/scope.py). Non-security, entertainment, or trivia queries return verdict: "inconclusive" without invoking model providers.

Active Defense & Containment (Phase 1)

Active Defense closes the loop between threat detection and operational remediation through deterministic containment adapters, dual-custody approval gates, out-of-band verification probes, and scheduled TTL recovery.

Protection Scope & Boundaries

Boundary Distinction:

1. Ternline Ingestion Protection: Built-in Redis IP blocking and rate limiting immediately reject malicious requests targeting Ternline's own /v1/events API.

2. Customer Application Protection: Blocking traffic to your own customer microservices requires integrating with our HMAC-SHA256 signed webhooks or deploying gateway middleware that queries Ternline status.

Protection Modes

  • OBSERVE (Default): Containment actions are synthesized and recorded as dry-run audit entries. Zero infrastructure state changes occur.
  • ASSISTED (Human-in-the-Loop): Actions require explicit approval from an authenticated human operator via POST /api/v1/defense/actions/{id}/approve.
  • ENFORCED (Autonomous Bounded Containment): Pre-authorized low-risk actions (e.g. temporary IP blocks with TTL) execute autonomously. High-risk actions (API key revocation) always enforce mandatory dual-custody sign-off.

Dual-Custody Approvals & Safeguards

Anti-Self-Approval Enforcement: An operator who proposed or planned a containment action can NEVER approve it. Approvals submitted by the requester or via automated service accounts return HTTP 403 Forbidden.

State Verification & Automated TTL Expiration

Before advancing an action to VERIFIED_ACTIVE, VerificationManager runs out-of-band state probes. Actions configured with a Time-to-Live (TTL) are scheduled in a Redis sorted set (ZSET). Expired actions are reverted either manually or automatically by invoking POST /api/v1/defense/actions/reconcile-expirations via a scheduled job or cron worker.

Threat Intelligence & Incidents (Phase 2)

Phase 2 aggregates security findings across microservices into unified incident cases and maintains tenant-scoped Indicators of Compromise (IOCs).

Incident Correlator Engine

When findings are created by Fast Track or attack simulations, IncidentCorrelator groups them by:

  • Shared Distributed Trace: Groups multi-hop attack stages sharing a W3C trace ID (e.g. api-service → worker-service → database-service).
  • Shared Primary Entity: Attacker IP address or user identity across active incident windows.
  • Severity Escalation: Composite incident severity automatically escalates from medium to critical if subsequent higher-severity stages occur.

Incident Lifecycle & Forensic Timelines

Incidents progress through a managed lifecycle (open → investigating → contained → resolved). Querying an incident via GET /api/v1/incidents/{incident_id} retrieves linked findings, affected entities, and a multi-service event timeline reconstructed from distributed traces.

Coordinated Multi-Entity Containment

Security Architecture & Limitations

Tenant Isolation Invariants

  • All SQL queries and database models strictly enforce tenant_id filters.
  • Redis state keys and Lua script counters are namespaced by tenant (ternline:{tenant_id}:...).
  • Cross-tenant telemetry leaks are prevented by server-side tenant derivation from authentication tokens; caller-supplied tenant headers are overwritten.

Secret & Credential Handling

  • API keys are stored strictly as SHA-256 hashes (key_hash); plaintext keys are never persisted.
  • User passwords are encrypted with salted PBKDF2-HMAC-SHA256 with 600,000 iterations.
  • Email verification uses 256-bit cryptographically random tokens with 24-hour expiration.
  • The Python SDK automatically redacts known secret patterns (passwords, tokens, keys, SSNs) client-side before transmission.

Application Protection Scope & Limitations

Integration Requirement: Ternline is an evidence-led detection and containment orchestration platform. It is not an inline network proxy or inline WAF. Blocking traffic to customer applications requires the customer to configure gateway webhooks or consume Ternline containment status via middleware. Ternline's built-in blocklists protect Ternline's own ingestion perimeter.
